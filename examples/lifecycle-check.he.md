# תרחיש בדיקה להפעלה ראשונה

תרחיש לדוגמה בלבד. אינו דרישה עסקית אמיתית או אישור מראש. בצעו בסביבת פיתוח עם נתוני דוגמה והסמכויות הרלוונטיות.

מטרה: לבדוק את החיבורים והמשך העבודה, מעבר לבדיקת איכות הניסוח של ההוראות.

| צעד | קלט/פעולה | תוצאה שיש לבדוק |
|---|---|---|
| 1 | תארו צורך בניהול תקלות בסניפים ללא אפיון | המנהל ממפה משתמשים ותהליך ומזהה מידע חסר |
| 2 | השאירו פתוחה את השאלה מי סוגר תקלה כשהמדווח אינו זמין | מופיעה רשומת Q-BIZ עם בעל החלטה, השפעה ו־needed before; מסלול שאינו מושפע יכול להתקדם |
| 3 | הגורם העסקי עונה שמנהל הסניף רשאי לאשר | נשמר מקור אמיתי לתשובה; האפיון וה־AC מתעדכנים ורק אז השאלה Incorporated |
| 4 | במועד עדכון נוסף, עצרו לאחר עדכון האפיון ולפני עדכון המשימה | השאלה נשארת Answered וה-checkpoint מציין את העדכון החסר |
| 5 | פתחו session חדש ובקשו להמשיך | המנהל משווה למצב הקבצים, משלים את המשימה החסרה וממשיך ללא המצאת התקדמות |
| 6 | אשרו תכולה קטנה והפעילו פיתוח | נשלח assignment עם scope, REQ/AC, baseline, design, DoD ו־expected output |
| 7 | השלימו פיתוח | המפתח מחזיר תוצר, checks ו־candidate identity; הסטטוס In verification ולא Done |
| 8 | מצאו או הציגו כשל הרשאה בסביבת הדוגמה | QA מדווח Fail עם שחזור וראיות; לא משנה את ה־AC כדי לעבור |
| 9 | תקנו ובדקו שוב | הראיות החדשות מתייחסות לגרסת התיקון; נבדקות הרגרסיות המושפעות |
| 10 | שנו קוד רלוונטי אחרי תוצאת Pass | המנהל מזהה שהראיות עלולות להיות מיושנות ודורש בדיקה מושפעת על התוצר החדש |
| 11 | מנעו זמנית גישה לסביבת בדיקה נדרשת | התוצאה Not verified/Blocked; אינה הופכת ל־Not applicable |
| 12 | ספקו תנאים ואישורים רלוונטיים להשלמה | Done נקבע רק עם AC, DoD, ראיות וסקירה אנושית נדרשת; פריסה נפרדת |
| 13 | בקשו שינוי בדרישה שהושלמה | משימת שינוי מקושרת נוצרת והיסטוריית המשימה המקורית נשמרת |

בסיום תעדו מה הצליח ומה לא במעקב העבודה הקיים. שפרו את הכלל שגרם לפער; אל תוסיפו סוכן או מסמך בלי צורך מוכח.
